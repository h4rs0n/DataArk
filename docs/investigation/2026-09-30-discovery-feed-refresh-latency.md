# discovery-feed/refresh 延迟调查

调查日期：2026-09-30。对象：本地 Compose 部署中的 `POST /api/recommendations/discovery-feed/refresh`，用户 ID 1。

## 结论与实际请求

12 秒主要由同步 LLM 排序与重复候选查询叠加造成。已经在服务日志找到 12.04 秒的成功请求，不是仅根据代码推测。

| 请求完成时间（北京时间） | HTTP 状态 | 服务端总耗时 | LLM 耗时 | LLM 占比 | 非 LLM 耗时 |
| --- | --- | --- | --- | --- | --- |
| 2026-09-30 19:25:49 | 201 | 10.760 s | 8.103 s | 75.3% | 2.657 s |
| 2026-09-30 19:26:13 | 201 | 12.040 s | 9.388 s | 78.0% | 2.652 s |

总耗时来自 Gin 日志，精度受日志格式影响；LLM 耗时来自紧邻该请求完成日志的 `llm_call` 事件，两次均为同一用户的 `recommendation_rerank` 成功事件，并与数据库批次 103、104 的创建时间和模型字段匹配。

两次非 LLM 耗时几乎相同，接口总耗时差 1.280 秒，LLM 耗时差 1.285 秒，说明这两个样本的耗时波动几乎全部发生在 LLM 环节。样本只有两次，不能推导长期 P95/P99。

## 同步调用链

1. `api/api/recommendation.go:88`：认证后调用 `RefreshDiscoveryFeed(ctx, userID, 10)`；等函数完整完成后返回 201。
2. `api/recommendation/discovery_feed.go:65`：获取 `userID % 64` 对应的进程内互斥锁。
3. `discovery_feed.go:74`：读设置；`78`：重建用户画像。
4. `discovery_feed.go:82`：查询未曝光或内容更新的候选，完成硬过滤与组池。
5. `discovery_feed.go:86`：同步调用 LLM 排序。
6. `discovery_feed.go:108`：事务替换旧批次，逐条写入推荐项和曝光状态。
7. `discovery_feed.go:131`：补充候选信息，然后返回快照。

这条调用链没有启动新一轮文章抓取，也没有在请求内逐篇做文章 LLM 评估。已有候选来自后台任务。

## 主耗时：一次完整 LLM 请求

`api/recommendation/rerank.go:15` 强制调用 reranker；有候选时，模型失败会返回错误，不会直接发布规则排序结果。空候选池则跳过模型。

默认候选池为 100，默认重排上限为 30。接口需要 10 条，但模型输入是排序后的前 30 篇候选，字段包括标题、摘要、主题、来源、发布时间、质量与深度，再附用户画像。见 `rerank.go` 的 `buildRerankCandidates` 与 `buildUserProfileHint`。

`api/recommendation/openai_provider.go:49` 要求模型输出候选 ID、名次、中文推荐理由和置信度。`api/llm/client.go:133` 发起一次 `/chat/completions` 请求，`PostJSON` 读取完整响应体后才解析结果，没有流式返回或在此路径内自动重试。

| 完成时间 | 模型 | 输入 tokens | 输出 tokens | reasoning tokens | cached tokens |
| --- | --- | --- | --- | --- | --- |
| 19:25:49 | mimo-v2.6-flash | 4814 | 410 | 0 | 0 |
| 19:26:13 | mimo-v2.6-flash | 5116 | 504 | 0 | 0 |

实际排序调用为 8.103 / 9.388 秒。日志中的 `duration_ms` 包含客户端请求、完整响应读取和 JSON 解析；缺少 DNS、连接、TTFB、供应商排队、prefill 与 decode 的分段信息，因此不能进一步断言这 9 秒具体由供应商哪个内部环节造成。

模型已经关闭 thinking，实际 reasoning tokens 也是 0；不能归因于隐藏的长推理。此次 cached tokens 为 0，未观察到供应商缓存收益。

重排的 `max_tokens` 是 2048，实际输出为 410 / 504；2048 是上限，不是固定生成量。`discover-timeout` 默认虽为 12 秒，但本接口不调用抓取器，两次均成功返回，也不是抓取超时导致固定等待 12 秒。

## 次耗时：五次候选查询

`api/recommendation/selection_v3.go:178` 的组池策略先为每个来源收一篇，目标达到 `poolSize` 个不同来源。默认 `poolSize=100`，每页读取 `poolSize*4=400` 篇；来源重复文章放入 overflow，直到达到来源目标、耗尽候选或达到扫描上限后才补池。

因此组池并非读到 100 篇或 10 个来源就停止。最终只使用前 30 篇作模型输入，却可能为获得 100 个来源读取几千篇。

| OFFSET | 19:25 请求耗时（ms） | 19:26 请求耗时（ms） |
| --- | --- | --- |
| 0 | 366.275 | 363.949 |
| 400 | 357.695 | 380.612 |
| 800 | 366.784 | 393.788 |
| 1200 | 432.710 | 431.932 |

| 合计 | 1912.470 | 1966.257 |

五页均返回 400 行，共读取 2000 行。12.04 秒请求中这部分占 16.3%；扣除 LLM 和已记录的五次分页，剩余约 0.686 秒，包括画像、其他查询、事务、响应组装等，没有分段埋点，不能精确分配给其中某个步骤。

调查时只读重算当前候选分布，用户有 7 条生效来源屏蔽规则；按用户屏蔽、归档、深读和显式反馈过滤，并以代码使用的来源名优先、主机名兜底规则计数：

| --- | --- | --- |

前四页仍达不到 100 个来源，第五页才能凑齐，解释了日志中的连续五次查询。后台持续处理文章，用户曝光状态也已包含这两次刷新，因此这里是调查时快照的验证，并非还原历史事务快照。该计数用于验证来源集中和后置屏蔽的影响，没有完整重放历史与冷却算法。

当前前 2000 行中 `gohugo.io` 有 433 行、`www.flysnow.org` 有 238 行、`securitylab.github.com` 有 223 行，说明高产来源集中会放大组池扫描。屏蔽过滤在 Go 循环中执行，被屏蔽来源仍先占据 SQL 分页结果。

## PostgreSQL 执行计划定位

环境为 PostgreSQL 17.10。调查时统计估计：候选表约 13.5 万行，material 约 13 万行；实际推荐历史 1564 行。用户当前有效反馈 20 条、互动状态 185 条；正向画像向量为空数组，本次用户不执行向量召回查询。

对日志中原始第一页与第五页 SELECT 执行 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`，均在只读事务内，未修改数据库结构或数据。

候选查询的更新例外条件使用相关子查询：

```sql
EXISTS (
  SELECT 1
  FROM recommendation_items AS prior_item
  WHERE prior_item.user_id = 1
    AND prior_item.content_version < discovery_candidates.content_version
    AND (
      prior_item.material_id = discovery_candidates.material_id
      OR (
        discovery_candidates.dedupe_key <> ''
        AND prior_item.dedupe_key = discovery_candidates.dedupe_key
      )
    )
)
```

执行计划显示：

- 该子计划对 `recommendation_items` 做 `Seq Scan`，执行 1026 次，单次约 0.315–0.323 ms，每次过滤约 1563 行。
- 约 160 万次历史行检查被每一页重复执行。第一页相关子计划约占 0.33 秒，整页约 0.379 秒；只读改写实验也验证了它是主要数据库瓶颈。
- 相关子计划产生约 53.2 万次 shared buffer hit；这是重复页访问次数，不代表读取了 53.2 万个不同磁盘页。
- 存在 `recommendation_items(user_id)` 和 `recommendation_items(material_id)` 单列索引，但此 OR 相关条件下实际计划选择了重复顺序扫描。不能简单归因于数据库完全没有索引。
- `discovery_candidate_details` 是复合视图，`SELECT *` 附带正文、来源属性、embedding 模型、归档和独立来源计数等投影；其中 7 个投影子计划在第一页各执行 400 次，第五页各执行 2000 次。
- 第五页 `OFFSET 1600` 需要处理 2000 行再丢弃前 1600 行；原计划出现 external merge 排序，进一步增加开销。

## 只读优化实验

实验把历史记录分别按 `material_id`、非空 `dedupe_key` 预聚合 `MIN(content_version)`，与候选连接，用聚合版本小于当前版本判断“曾推荐过较旧版本”。原查询要求存在任一较旧版本，所以这里必须用 MIN，不能误用 MAX 改变语义。

| 只读 SELECT 方案 | 数据库执行耗时 |
| --- | --- |
| 原始第一页 | 378.556 ms |
| 原始第五页 | 402.454 ms |
| 原始第一页，仅取 ID/material/URL/质量/时间 | 343.959 ms |
| 历史预聚合连接，第一页，保留完整字段 | 47.533 ms |
| 历史预聚合连接，第五页，保留完整字段 | 85.638 ms |
| 历史预聚合连接，第一页，精简字段 | 23.903 ms |

只精简字段改善有限，因为重复历史扫描仍存在。预聚合连接将第一页执行耗时降低约 87%，第五页降低约 79%。

在同一只读事务中，用双向 EXCEPT 检查原始与预聚合查询全部候选 ID：两边都是 2345 个候选，差集为 0。该检查验证当前数据下 SQL 过滤集合一致，不替代生产回归测试，也不覆盖最终来源组池与排序结果。

以上是单轮数据库执行计划计时，缓存、并发与数据变化会影响结果；不含 Go 扫描、网络传输和完整接口开销。不能直接把实验数值当作上线后端到端 SLA，也不能据此承诺接口降到 1 秒。

## 优化优先级

1. **解决用户等待完整模型调用的问题。** 若要求立即响应，可提前生成下一批并在刷新时取已完成快照；或接口创建后台任务返回 202，前端显示生成状态并查询结果。仅改成 202 改善响应等待，任务本身仍需完成 LLM。预生成需要再次校验屏蔽、曝光和内容版本，避免重复推荐。
2. **改写历史相关子查询。** 预聚合连接已有当前库验证，能直接减少五页重复扫描。正式实现应补 PostgreSQL 集成验证，覆盖同 material、多 dedupe、空 dedupe、不同版本与多用户；如选索引方案，需要 numbered Goose migration 和新执行计划证据。
3. **减少来源组池浪费。** 将用户屏蔽和显式状态过滤前移；评估直接召回来源代表、用游标替代 OFFSET，或让发现流的来源目标与重排上限协调。改来源目标会改变多样性，需要行为评估，不能只把 100 改成 10。
4. **缩小候选投影。** 召回阶段读取必要字段，最终候选再补快照字段；避免为被过滤文章加载正文与重复来源子计划。该改动应排在相关子查询之后。
5. **测量并压缩模型输入输出。** 增加 prompt 大小、候选数、TTFB、完整响应耗时；验证摘要截断、候选上限和推荐理由长度对质量与耗时的影响。当前模型已禁 thinking。换模型、缓存和更短输出的收益尚未通过实验验证。
6. **补齐分段观测。** 记录 lock wait、profile、history、pool scan（页数/行数/来源数/排除原因）、rerank、persist 和 attach；关联请求 ID、用户 ID、批次 ID。发现流调用了全局排除计数，但最终快照没有保存这些统计，可评估移出请求关键路径。

即使把全部非 LLM 的约 2.65 秒消除，在同样模型耗时下仍需要约 9.39 秒。若目标是明显低于数秒，应同时处理模型等待方式和数据库成本。

## 其他开销与证据边界

- 互斥锁覆盖完整生成过程，包括模型等待。同用户并发刷新会排队，不同用户 ID 模 64 相同也会互相阻塞；锁不感知 context 取消。现有日志不能证明这两次请求有明显锁等待。
- 每次刷新完整重建画像，设置还会被重复读取；历史、已见主题和作者也在请求内读取。数据增长后可能放大，但当前无法单独归因其耗时。
- 事务逐条插入 10 个推荐项、写曝光，并有创建 hook 额外查询。可以考虑批量化，但不能把这部分当成本次主要瓶颈。
- 同期后台抓取与处理任务运行，日志也有其他慢 SQL；没有证据把它们全部算入该 HTTP 请求，或者直接归因于连接池耗尽。
- 前端 `DiscoveryFeedPanel.vue:96` 在 POST 返回后还等待每个条目的反馈查询，因此按钮停止 loading 的时间可能比接口本身更长；它不能解释 Gin 已记录的 12.04 秒。
- 普通 GET 读取现有发现流的一条日志耗时为 35.13 ms，刷新多出的同步生成工作才是关键差异。

调查只读取已有日志与数据库，并执行只读 SELECT/EXPLAIN；没有重新触发刷新消耗候选、调用收费模型、重启服务或修改业务实现。此次新增调查报告，未提交 commit。
