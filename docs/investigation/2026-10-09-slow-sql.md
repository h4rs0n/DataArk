## 结论

当前持续慢查询的主要原因是：**黑名单文章使查重恢复无法收敛，反复触发全库恢复；代表文章资格查询的行数估算严重偏低，产生大量嵌套索引访问。** 恢复流程还逐个检查评估作业，放大了每次恢复的总成本。

当天日志中的最大历史问题已经修复：原来每取 250 条评估目标都会重做全库查重资格计算，现已改为一次读取目标集合。另一批历史单篇慢查询对应的 `material.current_version_id` 索引也已存在。不能把整天累计日志都当作当前版本仍有的问题。

本次只读取日志、代码和运行数据库，并在只读事务中执行查询计划分析。没有修改业务代码、数据库结构或全局参数，没有重启服务。报告不包含原始文章、域名、凭据或完整运行日志。

## 原因一：黑名单成员被永久视为“待恢复”

运行库快照：

- 查重模式为 `active`，当前 run 为 1，`pending_assessment=false`。
- 当前 run 有 94,873 个成员，其中 **340 个 `applied=false`**。
- 这 340 个成员全部仍对应当前内容版本、全部命中域名黑名单、全部以自身为代表；没有任何可用且未命中黑名单的 ready 候选。
- 最近 10 分钟，这 340 个 representation 对应 **1,360 条新建查重作业**，即每个平均被再次创建 4 次。成员 revision 为 87–89，与反复处理一致。

代码形成了以下循环：

1. `dedupeRecoveryDrift`（`api/discovery/dedupe_runs.go:932`）直接统计所有 `applied=false`，没有区分黑名单阻塞与可修复状态，因此持续返回非零漂移。
2. `recoverDedupeJobs` 进入完整恢复：扫描不可用代表、扫描覆盖缺口、重投代表文章评估目标、清理评估队列。
3. `usableDedupeArticle`（`api/discovery/dedupe_index.go:182`）排除黑名单，因而这些文章没有安全代表。
4. `applyDedupeGroup`（`api/discovery/dedupe_runs.go:361–376`）在无可用代表时把成员设为自身代表，继续保留 `applied=false`，增加 revision，随后正常返回。队列因此将作业记为完成。
5. 查重作业唯一约束只覆盖尚未结束的状态（`api/jobqueue/dedupe.go:29`），已完成作业不阻止下一轮恢复再次入队。

定时器每分钟触发；实际日志中的完整扫描阶段约隔 **2–3 分钟**出现一次，例如 15:36:47、15:39:17、15:41:08。恢复本身需要时间，不能把定时器频率直接解释为每分钟都完成一轮。

原设计在无漂移时只每 30 个 tick 做一次兜底全扫描；当前 340 个无法推进的成员使这个节流机制持续失效。恢复与爬取调度独立，因此关闭爬取队列自动启动并不会阻止这类恢复 SQL。

## 原因二：资格过滤严重低估行数，选择了昂贵的连接计划

`FilterDedupeAssessmentCandidates`（`api/discovery/dedupe_index.go:533`）要求成员满足：当前 run、当前内容版本、`applied=true`、`representation_id=representative_id`。该条件通过 `EXISTS` 与候选投影连接。

当前成员中 94,654 / 94,873（约 **99.77%**）为自身代表；执行计划对这项同表两列相等条件的估算明显偏低，后续版本和 material 连接进一步放大误差。查重成员统计在当天下午自动更新过，不能简单归因于忘记运行 `ANALYZE`。

对日志中的原始 SELECT 做只读 `EXPLAIN (ANALYZE, BUFFERS)`：

| 当前全部代表文章入队目标 | 1,434ms | **1 / 90,784** | 1,468,820 / 106,492 |
| 待评估文章恢复 | 1,398ms | **1 / 90,471** | 1,469,719 / 105,280 |

全部目标查询仍扫描约 9.4 万已应用代表，再对候选、material、文章状态等进行约 9 万次嵌套索引访问。当前版本只选择入队所需的三个字段，已避免整篇正文投影；主要问题是连接路径与重复访问。

覆盖缺口查询虽然只返回 250 条，仍检查约 5.2 万 representation，并进行了约 4.9 万次覆盖资格检查。不可用代表查询排序约 9.5 万成员、检查约 5.3 万候选才找到 250 条。`LIMIT 250` 并不能保证底层只处理 250 条。

`shared read` 表示 PostgreSQL 共享缓冲区未命中后读取的数据块；它可能由操作系统缓存提供，不能直接等同于物理磁盘读取。当前 `track_io_timing` 关闭，无法准确拆分 CPU 与实际磁盘耗时。执行计划指标解释参见 [PostgreSQL 17 EXPLAIN 文档](https://www.postgresql.org/docs/17/using-explain.html)。

### 只在事务内调整参数的对照

对同一全部目标 SELECT 使用 `SET LOCAL`，事务结束即恢复参数：

| 条件 | 耗时 | 观察 |
| --- | ---: | --- |
| 原配置，`work_mem=4MB` | 1,434ms | 约 3MB 外部排序，有临时文件读写 |
| `work_mem=32MB` | 1,342ms | 消除排序落盘，但仅改善约 6% |
| `enable_nestloop=off` | 926ms | 结果仍为 90,784 行，shared hit 降至 98,059 |

连接策略调整的改善幅度大于增加排序内存，支持“连接计划是主要成本”的判断。每种条件只测一遍，运行库并发与缓存状态会变化，因此这些数字是诊断证据，不是性能承诺。**不要据此在全局关闭 nested loop**，点查询仍需要它。

## 原因三：恢复过程逐个校验大量评估作业

`PruneAssessments`（`api/jobqueue/dedupe.go:63`）每页读取 250 条评估作业，然后对每条执行资格回调。回调调用 `ArticleDedupeQualification`（`api/discovery/dedupe_index.go:442`），分别查询设置、当前成员、代表文章、可用候选和代表成员；代表文章读取还包含正文。

运行库当时有约 **18.1 万条尚未结束的评估作业**。若一轮扫描覆盖整个队列，逐条资格验证会放大成大量数据库往返。很多单条查询低于 200ms，不会出现在 slow SQL 日志中，但仍占用恢复时间与数据库资源。

这是代码和队列规模证实的成本放大点；目前缺少各恢复阶段的耗时埋点，不能将完整恢复间隔中的全部时间都归因于该回调。

## 修复优先级与验收建议

1. **先让恢复收敛。** 将黑名单/不可用成员与可执行的待查重成员区分，常规漂移只触发可以推进的修复；黑名单、版本或候选状态变化后再重新激活。不要直接把所有阻塞成员改为 `applied=true`，必须保留评估与推荐资格的正确性。验收：阻塞成员不再反复创建完成作业，无变化时完整恢复遵守兜底周期。
2. **合并资格查询与批量校验。** 减少当前版本和 material 的重复连接，验证改善代表条件行数估算的查询形式、表达式统计或适配的部分索引；将评估队列逐条资格检查改为集合或批量操作。如需生产索引，走编号 Goose 迁移。验收：相同资格结果、代表/非代表/黑名单/版本切换行为正确，执行计划和数据库往返数量显著减少。
3. **最后再调资源参数。** 排序落盘是次要放大因素，单纯提高 `work_mem` 无法修复恢复循环或错误行数估算。需要结合连接并发评估内存预算，并用同负载重复测量。
4. 补充恢复阶段耗时、扫描行数、有效/阻塞漂移和新增作业数指标；按修复后新时间窗口验证，避免当天旧日志淹没当前效果。

本次数据库活动快照没有发现持续阻塞锁；这不排除历史短暂锁等待。没有启用 `pg_stat_statements` 或逐语句服务端耗时日志，结论基于 GORM 日志、运行库数据、代码路径和只读计划对照。调查时没有活动 Batch 运行，主要慢查询均属于查重/评估恢复路径，未发现指向百炼 Batch 调用的慢 SQL 证据。

## 修复与验收

### 已完成的变更

1. **恢复收敛。** 漂移探测只将当前版本、有正文和文章状态、且首个 ready 候选未被黑名单屏蔽的成员计入有效漂移。阻塞或过期成员保留 `applied=false`，不会因每分钟探测或兜底全扫描反复入队。删除黑名单规则后无需批量改写成员状态，资格变化会使成员重新进入可处理集合。黑名单增删同时将受影响查重组的 ready 候选标为 pending，让可用成员在下一次常规探测中触发修复；已应用但投影被标记 pending 的成员也会重新应用。
2. **覆盖扫描一次计算。** `dedupe_recovery.go` 将首个 ready 候选、可用的当前文章及有效代表集合分别计算并物化，再一次读取需要修复的 representation ID。替代原来的分页缺口扫描和逐代表寻找替代成员，避免重复读取正文投影、重复查询最小候选 ID 和重复检查全库资格。
3. **评估目标使用窄查询。** 查重与文章评估恢复共用 `PendingAssessmentTargets`，直接连接候选、material 和文章状态，只读取 material ID 与内容版本，保留代表、黑名单、到期时间和查重模式过滤，并按 material 去重。
4. **修正查询估算。** 迁移 `000042_dedupe_recovery_queries.sql` 增加代表布尔表达式统计、已应用代表的覆盖索引，并执行 `ANALYZE`。代表条件使用 `(representation_id=representative_id) IS TRUE`，使表达式统计参与估算；当前版本的相关等式以布尔 `CASE` 验证，避免被作为独立连接条件叠乘。黑名单精确或子域名匹配保留为相关存在性检查，避免反连接将几乎所有文章估算为已屏蔽。表达式统计随后续自动分析更新，参见 [PostgreSQL CREATE STATISTICS](https://www.postgresql.org/docs/17/sql-createstatistics.html)。
5. **批量校验评估队列。** `PruneAssessments` 每页最多 250 个目标只调用一次集合资格查询，不再对每个作业读取设置、代表正文和评估覆盖信息。取消仍使用 River 的取消 API，并保留 `dedupe_superseded` 标记；运行中的作业不被清理。
6. **恢复阶段日志。** `dedupe recovery sweep` 记录 `actionable_drift`、`inactive_unapplied`、`gap_targets`、`assessment_jobs_scanned`、`cancelled`、`gap_ms`、`enqueue_ms`、`prune_ms` 和总耗时。`inactive_unapplied` 包含黑名单、不可用和过期成员；`gap_targets` 是投递目标数，队列唯一约束可能去掉重复投递，不应解释为实际新增作业数。`assessment_jobs_scanned` 统计具有 material ID、参与批量资格检查的目标。

使用独立 PostgreSQL 17 容器与临时数据库，执行真实 Goose 迁移和 River 队列路径；未修改运行数据库或全局资源参数。
